# 重构原则（项目规则）

## 目标
降低 `Form1.cs` 复杂度（已 1.7 万+ 行），通过服务化抽取提升**可维护性、性能、稳定性**。
当范围不清或取舍两难时，一律选择最利于这三者（尤其是稳定性）的方案，而非最小改动。

## 硬性原则
1. **稳定性优先**：任何重构都不得改变运行时行为。重点保护：检测线程时序、IO/PLC 输出时机、
   良率统计（`E:\生产统计`/`E:\每日统计`）、方案切换排空逻辑。每步完成后**必须编译验证通过**。
2. **增量、可回退**：分阶段小步迁移，每步独立可编译、可回退；禁止一次性大改整段逻辑。
3. **薄封装优先**：服务以"所有权收口 + 委托既有实现"为主，不重写业务逻辑；行为等价是硬约束。
4. **依赖注入**：新服务在 `Core/Infrastructure/AppHost.cs` 组合根注册为单例，业务代码经
   `AppHost.Services.Resolve<T>()` 解析，禁止散落 `new`。
5. **保留语义、消除重复**：保留既有具名语义（如 `myjob1..12`）优于强行索引化；优先消除
   `case "1".."12"` 这类逐路重复，而非机械搬迁。
6. **性能不退化**：不在热路径引入额外同步/分配；保持既有并发模型（线程/事件/委托）不变。
7. **JobService 抽取顺序**（已确认）：Step1 所有权收口（myjobs[12]/yunxing）→ Step2 生命周期与
   触发路由（InitializeJobManager/StartRun/StopRun/ApplyCommTrigger/DataChange_*）→
   Step3 检测核心（getrecord 的 block.Run+Outputs 与 case1..12 的 IO/PLC 输出，用 ok(i)/ng(i) 参数化）。
   各步编译验证、行为对照。
