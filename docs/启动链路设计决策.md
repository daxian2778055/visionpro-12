# 启动链路设计决策（2026-11-24 复审后）

> 背景：设备重上电首次启动反复出问题，连续多轮修复后做专项复审。本文件固化「为什么这么设计」，避免后续维护者改回旧写法。

## 1. 触发模式以 ini 为权威源（关键决策）

**决策**：相机触发模式（`triggerMode`）的权威来源是 `code.ini [cameraN] triggermode`，**不是 VPP 方案里的 `triggermode` 输入**。

**原因**：加载时序上，`managerState=Loaded` 在 VPP 文件加载完就置位（Form1.cs:1043），但 12 路 `myjob.block` 要到 `initialize_FormSet`（UI 线程）才绑定。`trriger_set` 在后台线程读 block 时可能还是 null → 触发模式停留在初始空值 → 运行期被误判、相机白采图/过载刷屏。这个时序耦合很深，动加载同步风险高（历史上多次事故），所以采用"以 ini 为准"绕开。

**体现**：
- `Form1.DisplaySettings.cs:ReadCfgTriggerMode(section)`：读 ini，空值/非法值统一回退"通讯触发"（与设计器默认值一致），12 路 × 4 处共 48 处统一走它。
- `Form1.ErrorDisplay.cs:ShouldProcessImageCallback`：内部 triggerMode 为空时，从 ini 回填真实值，而不是硬编码当"连续运行"。
- 勿改回：不要恢复"优先从 block 读 triggermode 且 block 为空就不赋值"的写法。VPP 的 `triggermode` 输入仅作可选参考。

## 2. 设备名 → 槽位映射只有一份口径

**决策**：`HikCameraEnumerator.Normalize`（去 `\0` + Trim）+ OrdinalIgnoreCase 是唯一口径。

**原因**：bnOpen 用 `MapToSlots`（归一化 + 忽略大小写），而 timer2 按名重扫原来用精确 `==`。重上电后相机 UserDefinedName 若大小写/尾随空格漂移，会出现"开相机能绑、断线连不回"。重复名时两者取第一个/最后一个不同，可能错绑槽位。

**体现**：`IsConfiguredCameraName` / `TryResolveCameraSlotByName` 都调用 `HikCameraEnumerator.Normalize` 并取第一个匹配；`nameMatched` 在 slot 解析成功后才置位（避免 device1[] 索引错位）。

## 3. 0 台相机也启用发现重连

`bnOpenCore` 收尾无条件 `EnableCameraReconnect()`；timer2 内对"有槽位为空"的发现枚举做 3s 节流，避免全网广播风暴。原因：原来仅 `CountOpenedCameras()>0` 才启用，设备重上电一台没连上时重连永不启动、软件永久停在无相机态。

## 4. 取流失败交给重扫自愈

首次运行 `PrepareCameraGrab` 失败时，`ReleaseFailedCameraSlot`（ErrorDisplay.cs）完整销毁句柄并置 null，交给 timer2 按名重扫重建。原来只置 `yun=0`，相机对象仍在 → 四条恢复路径全部失效的永久僵尸槽。
