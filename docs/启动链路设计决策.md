# 启动链路设计决策（2026-11-24 复审后）

> 背景：设备重上电首次启动反复出问题，连续多轮修复后做专项复审。本文件固化「为什么这么设计」，避免后续维护者改回旧写法。

## 1. 触发模式生效优先级：合法 VPP block → ini 兜底

**决策**：保持当前实际行为——VPP `triggermode` 输入是已知三种模式时优先采用；block 未绑定、读取异常或值非法时，才读 `code.ini [cameraN] triggermode`。ini 为空/非法时统一回退"通讯触发"。

**原因**：加载时序上，`managerState=Loaded` 在 VPP 文件加载完就置位，但 12 路 `myjob.block` 要到 `initialize_FormSet`（UI 线程）才绑定。`trriger_set` 在后台线程读 block 时可能还是 null，因此必须保留 ini 兜底，避免触发模式停留在初始空值。当前代码并未把 ini 改成唯一权威源；擅自调整 VPP/ini 优先级属于产品行为变更，需单独确认。

**体现**：
- `Form1.DisplaySettings.cs:ReadCfgTriggerMode(section)`：读 ini 后统一走 `FrameAccounting.ResolveTriggerMode`，空值/非法值回退"通讯触发"。
- `Form1.ErrorDisplay.cs:ShouldProcessImageCallback`：内部 triggerMode 为空时，用同一合法化规则从 ini 回填；回退成通讯触发后必须按通讯触发门控判定，不能直接放行全部帧。
- 勿改回：不要恢复"block 为空就不赋值"或"非法配置直接当连续运行放行"的写法。若要改成 ini 单一权威源，须先明确 VPP 输入是否还参与 VisionPro 作业内部判定，并补对照测试。

## 2. 设备名 → 槽位映射只有一份口径

**决策**：`HikCameraEnumerator.Normalize`（去 `\0` + Trim）+ OrdinalIgnoreCase 是唯一口径。

**原因**：bnOpen 用 `MapToSlots`（归一化 + 忽略大小写），而 timer2 按名重扫原来用精确 `==`。重上电后相机 UserDefinedName 若大小写/尾随空格漂移，会出现"开相机能绑、断线连不回"。重复名时两者取第一个/最后一个不同，可能错绑槽位。

**体现**：`IsConfiguredCameraName` / `TryResolveCameraSlotByName` 都调用 `HikCameraEnumerator.Normalize` 并取第一个匹配；`nameMatched` 在 slot 解析成功后才置位（避免 device1[] 索引错位）。

## 3. 0 台相机也启用发现重连

`bnOpenCore` 的正常收尾与 0 设备/0 匹配早退都会 `EnableCameraReconnect()`；timer2 内对"有槽位为空"的发现枚举做 3s 节流，避免全网广播风暴。原因：原来仅 `CountOpenedCameras()>0` 才启用，设备重上电一台没连上时重连永不启动、软件永久停在无相机态。

## 4. 取流失败交给重扫自愈

首次运行 `PrepareCameraGrab` 失败时，`ReleaseFailedCameraSlot`（ErrorDisplay.cs）只释放本次实际操作的相机对象；槽位在等待期间已被替换时放弃收口，不拆新对象。释放前置 `_slotClosing`，拆除在转换专用锁内完成，交给 timer2 按名重扫重建。原来只置 `yun=0`，相机对象仍在 → 四条恢复路径全部失效的永久僵尸槽。
