# 注释与审计规范

## 两套标记并行，不互相取代

- **`★第N轮`**：时间序，记录修改当时的现场背景与实测数据。**保留不删**——它回答"当时为什么这么改"。
- **`ch:<稳定语义ID>`**：跨文件、跨轮次、跨项目可引用。回答"这个设计决策的语义是什么"，ID 不随轮次漂移。

新改动使用 `ch:` 标记；旧注释无需回溯重写。本项目已有的"★借鉴正泰版 R13"就是跨项目引用 `ch:R13` 的实例。

## ch: 格式

```
ch:<ID> <一句话原缺陷机制> → <现在怎么做> → <边界/不做什么>
```

ID 取自审计报告小节号（`Rxx` / `Px`），例如：

- `ch:R13 CSV 读缓存：每条结果整表读盘 → 按路径+长度+mtime 缓存行副本 → 写后立即刷新，外部改写即失效`
- `ch:P1-04 自动曝光：补偿值超出相机范围 → 先读 fMin/fMax 夹住再下发 → 读失败保留请求值`

## 三角索引

一条重要设计决策应在三处出现同一个 ID：

1. 审计报告对应小节（`docs/审计报告模板.md` 六段式）
2. 生产代码注释（`ch:<ID>`）
3. 测试文件头注释或测试项目 `csproj` 的源码链接说明

这样"报告 ↔ 代码 ↔ 测试"可互相定位，而不是散落在时间序注释里。

## 审计基线

每次重大变更前运行：

```
.\verify.ps1 -GenerateBaseline
```

生成 `audit-baseline.json`（相对路径 + SHA-256），随版本提交归档。
任何"报告说改了但源码已变"的争议可用哈希裁决；换机器也能复核（**不要写绝对路径**）。

## 禁止

- 不要为了"修复数量好看"把不同集合的问题数字相加。
- 不要把存疑项写成确定缺陷。
- 不要在报告里写未实际执行的验证（构建/测试/真机）。
- 不要让临时枚举值（帧号、时间戳）进入限流日志 tag 导致字典无界增长。
